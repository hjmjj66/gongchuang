## 3. 现有协议依据

依据：`工创赛屏幕驱动/屏幕与上位机串口通信说明.md`、`screen_protocol.py`、`interactive_screen_test.py`。现有文件只读参考。

### 屏幕发送给上位机

| 数据示例 | 含义 |
| --- | --- |
| `ROUTE,1,5,12\r\n` | 本轮人工确认路径 1、5、12 不可走 |
| `ROUTE\r\n` | 本轮人工禁行列表为空 |
| `CFG,1,2\r\n` | start1、stop2；分别对应规划节点 1、3 |

结尾是实际字节 `0D 0A`。路径范围为 1～12，协议要求单条 ROUTE 内编号不重复。用户所说“可以重复”允许人工结果与雷达结果重叠，最终合并时去重，不要求修改屏幕现有协议。

屏幕在路径页按 OK 后自行转到 `setup`；起终点页按 OK 后发送 CFG 并自行转到 `show_number`。CFG 即本次启动意图，协议没有另一条独立 START 消息。

### 上位机发送给屏幕

每条 ASCII 指令独立附加三个实际字节 `FF FF FF`。沿用文档建议，每条指令间隔约 100 ms，进入结果页后等待约 300 ms 再赋值。

任务码 `452+321+254+312` 按既有布局分两行：

- `show_number.t0.txt="452+321"`
- `show_number.t1.txt="254+312"`

第二行开头不额外添加加号。四组三位数字按字符串处理，保留前导零。

最终统计：先发送 `page result`，等待初始化完成，再分别发送 `t4.txt="抓取数"` 和 `t5.txt="放置数"`。按现有屏幕说明，结果页初始化时复制任务码，实测需确认数字和加号保持正确。

## 4. 后续测试文件的四阶段行为

### 阶段一：接收人工禁行路径

1. 打开已确认的屏幕串口，进入接收等待；保证接收已准备好后再提示用户操作屏幕。
2. 用户在 `select_routine` 选择不可走路径并按 OK。
3. 完整接收到合法 ROUTE 后，保存为本轮人工禁行列表，终端打印，例如：`人工禁行路径：1、5、12`。
4. 空 ROUTE 打印 `人工禁行路径：无`，仍允许继续。
5. 路径选择是本轮完整快照；同轮有效更新替换旧选择，不无条件累积历史选择。

### 阶段二：接收起终点并模拟启动

1. 等待合法 CFG；必须先收到本轮 ROUTE，空列表也算已收到。
2. 保存屏幕选项和规划节点：start1/stop1 对应节点 1；start2/stop2 对应节点 3。起点、终点独立选择，同区起停可用。
3. 终端明确打印两套编号，例如 `start2 → 节点3；stop1 → 节点1`，避免把屏幕编号 2 当成规划节点 2。
4. 从收到本轮有效 CFG 开始计时，立即打印 start/stop，约 2 秒后打印“比赛开始”，再提示第三阶段输入；不因重复 CFG 再次启动或重置倒计时。
5. 此测试不调用 `/mission/start`，不运行总比赛 bash 命令。

### 阶段三：终端输入任务码并显示

1. 终端提示输入四组三位数字，用英文 `+` 连接，例如 `452+321+254+312`。
2. 回车后校验结构；错误时说明格式并允许重输，不发送不完整数据。
3. 向既有 `show_number` 页的 t0、t1 逐条写入，上下两行各显示两组数字及中间加号。
4. 此处输入代替实际扫码，不调用摄像头。仅验证格式和显示，不替比赛程序判断颜色、位置等业务合法性。

### 阶段四：终端输入统计并显示

1. 分别提示 `成功抓取数：`、`成功放置数：`，每项单独输入并按回车，不沿用现有示例要求同一行输入两个数的方式。
2. 仅接受非负整数，允许 0；无效输入留在该项重新输入。
3. 两项均输入有效后切换 `result`，等待页面初始化，再写入 t4、t5，显示输入的两项统计并保留任务码。
4. 保持结果显示；退出测试不自动清空屏幕。再次开始一轮须明确操作，从路径选择阶段重新接收，清除本轮内存状态。
5. 本次统计完全采用人工输入，暂不实现计数规则或机构结果判断。

## 5. 接收与异常处理要求

- 按结束符维护持续接收缓冲，支持一条消息分多次到达、一次收到多条消息。
- 可参考或只读导入现有 `ScreenMessageParser`，不改动原文件；不得把发送示例的 `main()` 一并运行。
- 开机通知等非业务数据不能误识别为路径或启动消息；非法编号、非法 CFG 不推进阶段。
- 终端输入期间保持串口数据有序处理；重复或顺序错误的消息不能触发新一轮或重复启动。
- 串口断开或写入失败应报告失败并结束当前流程，不能继续打印“显示成功”。
- 发送日志只证明指令已写出，实屏显示是否正确由用户观察确认；当前业务协议没有显示成功 ACK。
- 开始新一轮时清理接收状态须在提示用户按 OK 之前完成，避免丢弃已经确认的选择。
- 不假定切页会自动取消旧高亮；若实测发现选择保留，提示用户在屏幕上核对，不修改 HMI。
