# 显示屏双向验证与比赛接入指导计划

## 1. 已确认目标与执行边界

用户已确认：

- 目前没有可编辑的屏幕工程，需要新建。
- 屏幕连接现有 RDK X5 上位机，屏幕通信程序在该上位机运行。
- 每次机构程序执行完成，对应次数加一；不要求视觉确认作为计数条件。
- 抓取统计包含原料区取料、粗加工区取回；放置统计包含粗加工区放料、暂存区平放和码垛。

最终功能：

1. 比赛前：左侧显示仓库中的赛场地图截图，右侧三个按钮分别选择初始启停区、终止启停区和一键启动。有效启动点击后倒计时 3 秒，进入现有比赛总程序。
2. 比赛中：扫码完成后持续显示本轮任务码；每次抓取或放置程序完成后更新对应统计，持续显示至本轮结束。

执行顺序固定为：准备最小屏幕工程 → 验收一“上位机到屏幕” → 验收二“屏幕按钮到上位机再到底盘” → 用户确认两项通过 → 正式比赛界面及程序接入。

当前只建立测试目录和编写本计划，不编写测试脚本或正式程序，不连接硬件执行运动。后续先编写验收所需的最小测试代码；正式功能必须等两项实物验收通过后再实现。

## 2. 测试目录约定

专用目录：`/root/工创/test/screen/`。

在两项验收完成前，新增屏幕工程、测试程序、配置、编译产物和验收记录全部保存在此目录内，运行测试时也以此目录为工作目录。现有底盘包只作为已实现接口复用，不在本阶段修改正式包。

建议后续按需创建以下内容，本次仅创建本计划：

| 相对路径 | 用途 |
| --- | --- |
| `hmi/` | 可编辑 `.HMI` 工程、字体、编译后的屏幕文件 |
| `config/` | 屏幕串口、波特率、页面及按钮 ID 等配置 |
| `scripts/` | 文字显示验收、按钮接收及三秒运动测试程序 |
| `records/` | 实测结果、串口帧与必要的运动时序记录 |
| `assets/` | 正式阶段使用的地图缩放资源 |

两项验收通过后，测试材料保留在此目录；正式屏幕节点再纳入 `ros2_ws/src/`，另行记录正式实现变更。

## 3. 现有文件与接口核查结果

### 3.1 屏幕驱动

原始示例：`/root/工创/工创赛屏幕驱动/screen_driver_example.py`。

- 示例标注型号为淘晶驰 `TJC4827T143`，4.3 寸，默认波特率 9600。
- 支持文字写入、数字写入、文字读回、页面切换。
- 指令以 `FF FF FF` 结束。
- 示例默认串口为 Windows 的 `COM5`，在 RDK X5 上必须换成实测 Linux 设备路径。
- 没有触摸事件接收、分帧、按钮处理及 ROS2 接入逻辑。
- 现有 `get_text()` 会清空接收缓存，并按一次读取截取响应；该实现只能作为独立文字测试参考，不能直接承担按钮与读回并行接收。

接线说明：`/root/工创/工创赛屏幕驱动/串口屏显示指令说明.txt`。其中旧部署描述为 RK3576，本次以用户确认的 RDK X5 为准。屏幕与 C 板是不同串口设备，必须分别识别；不得直接假定屏幕一定为 `/dev/ttyUSB0`。

### 3.2 底盘与比赛调度

| 已有接口 | 本次用途 |
| --- | --- |
| `/C/controll`，`agv_interfaces/msg/ControlCommand` | 验收二输出目标速度 |
| `/C/status` | 检查 PC 控制权、通信健康、运动许可及串口发送状态 |
| `/C/odometry`、`/C/chassis_odometry` | 观察实际车体速度和停车情况 |
| `/mission/start`，`std_srvs/srv/Trigger` | 正式阶段倒计时结束后启动比赛 |
| `/mission/state` | 判断 READY、RUNNING、FAULT 等状态及本轮身份 |
| `/mission/task_info` | 获取本轮有效任务码及 `run_id` |
| `/mission/qr_result` | 调度接受的最近一次二维码结果 |

底盘速度约定为 x 向前、y 向左、逆时针角速度为正。`vx_mps` 和 `vy_mps` 单位为 m/s；`omega_deg_s` 单位为 °/s。

现有底盘输入超时默认只有 0.05 秒，因此验收二必须约 50 Hz 持续发送速度，不能只发送一次后等待三秒。

已有 `cboard_diagnostics pulse` 可用于人工检查底盘链路，但它在启动时等待发现及健康检查；每次点击按钮才新启动该进程会产生额外延迟。按钮验收应提前建立 ROS2 通信并检查就绪，点击后直接进入运动状态，复用已有测试的时序和健康判断思路。

正式接入尚需补齐两处：

- 当前 `start_area`、`finish_area` 是调度节点启动时读取的只读参数，屏幕选择不能通过直接设置运行中参数生效。
- 当前 `/mission/state` 只有总步骤数，没有分开的抓取、放置统计；需从调度已确认的步骤账本生成统计快照。

## 4. 准备阶段：新建最小屏幕工程

因为没有 `.HMI` 源工程，先制作最小工程，不先做正式地图页面。

1. 核对屏幕后标型号、实际分辨率、触摸能力、当前波特率及 USB 转串口模块。480×272 仅作为示例型号对应的候选尺寸，必须以实物为准。
2. 在支持该型号的淘晶驰官方串口屏编辑器中创建工程。若编辑器需在 Windows 电脑运行，则在该电脑制作并保存工程，再将源文件和编译产物归档到测试目录。
3. 工程至少有一个测试页面、两个文本控件 `t0` / `t1` 和一个运动测试按钮 `b0`。记录页面 ID、按钮组件 ID 和文字控件名称。
4. 字库包含 `+0123456789`；如按钮采用中文，增加所需汉字。文本控件宽度、字库与字高应能完整容纳测试内容。
5. 配置按钮事件：优先选择“按下即发送组件 ID”，每次按下触发一次；本测试不等待松手。程序仅接受指定页面、指定组件的按下事件，忽略松开事件。具体选项与回传格式在编辑器和实机中核对。
6. 编译、下载到实屏并重启确认。具体采用存储卡或串口下载，以该型号支持的方式为准。下载工具退出后，再由测试程序独占串口。

按钮事件计划优先使用标准触摸帧：`65 <页面ID> <组件ID> <事件> FF FF FF`，其中标准按下事件为 `01`、松开为 `00`。先以实机抓到的帧确认，不将未核实的组件 ID 写死。若该型号需要显式编写发送事件，则在工程中约定固定格式，并同步修改接收解析器。

供电按实际屏幕模块说明接入。现有说明记录的是“USB 接上位机、模块 DC 电源座接外部电源”；其中外部电压范围只适用于对应模块，不能将该电压直接接到裸屏 5V 引脚。

## 5. 验收一：上位机向屏幕输入

### 5.1 目标

由 RDK X5 发送固定内容，让实屏完整显示：

```text
156+123+516+231
```

优先验证一行完整显示；若字体和屏宽不允许，则按逻辑分为两行，按上下顺序组成同一任务码：

```text
156+123
516+231
```

两行方案也用于正式大字号展示，避免为凑一行而缩小字体。字高要求参考现有说明中的不小于 12 mm，最终以规则及实屏有效字高核对。

### 5.2 实施步骤

1. RDK X5 识别屏幕串口，记录设备路径、波特率和连接方式；可用时优先使用 `/dev/serial/by-id/` 中的稳定路径。
2. 测试程序只打开屏幕串口，不创建任何底盘速度发布者。
3. 切换到测试页，向目标控件写入任务码；每条指令附带三个 `0xFF`。
4. 发送文字查询，接收并验证 `0x70 + 文本 + FF FF FF` 响应。单行比对完整字符串；双行分别比对后组合比对。
5. 保持页面显示，观察至少 30 秒；再次运行一次，确认结果可重复。

### 5.3 通过条件

- 实屏肉眼可见全部数字及加号，无截断、乱码、缺字和异常重启。
- 文字读回与目标逐字符一致；不能仅凭串口写入成功判通过。
- 内容在观察期间持续显示，再次测试仍正常。
- 记录实际页面、控件、串口和布局；标注“实屏验收一通过”。

## 6. 验收二：屏幕按钮触发三秒前进

### 6.1 目标与控制链路

```text
屏幕 b0 按下
  → 串口触摸事件
  → RDK X5 测试节点
  → /C/controll
  → 现有 C 板桥接
  → 小车前进三秒并停止
```

目标速度固定为 `vx_mps=0.1`、`vy_mps=0`、`omega_deg_s=0`，持续三秒。三秒从首次发布非零速度开始计时，不从进程启动、串口打开或 ROS2 发现开始计时。

这项验收验证按键回传和运动链路，不增加正式比赛的三秒启动倒计时。

### 6.2 点击前完成准备

- 启动现有 C 板桥接；确认 PC 控制权、健康反馈、里程会话和运动许可均有效。
- 停止 mission、网页调试和其他速度测试发布者。mission 即使处于 READY 也会发布零速，不能与本测试同时占用 `/C/controll`。
- 测试节点提前建立发布订阅，检测底盘接收端，绑定当前 `odom_session_id` 和 `motion_epoch`；就绪后屏幕按钮才允许触发。
- 实车车头方向留出可用空间。0.30 m 是速度乘时间的理想距离，验收不以精准走到 0.30 m 为条件。

### 6.3 测试状态与时序

1. `NOT_READY`：显示未就绪；点击不排队，也不在稍后自动补执行。
2. `READY`：接收指定按钮的有效按下事件，立即记录接收时间并进入 `MOVING`。
3. `MOVING`：约 50 Hz 发布指定速度；使用单调时钟计时。重复点击、长按产生的事件及松开事件均不延长或重启三秒运动。
4. 满三秒进入 `STOPPING`：主动连续发送零速至少 0.2 秒，观察实际速度回落，再结束本次测试。
5. 一次触发完成后须收到按钮松开，才允许下一次按下；运动中收到的点击不缓存。

串口接收采用持续缓冲和逐帧解析，兼容拆包、多帧合并和不同类型返回帧。按钮运行期间不能用会清空输入缓存的读回方法；不在串口回调中阻塞等待三秒。

通信或反馈异常、PC 权限或绑定变化、屏幕串口断开、竞争发布者出现时中止运动并尽力主动发零；正常退出也发零。进程异常失去输入时由已有 C 板桥接超时机制归零，恢复连接后不自动补跑旧按钮事件。

### 6.4 通过条件与记录

| 检查项 | 验收标准 |
| --- | --- |
| 按钮回传 | 一次按下被正确识别，只触发一次 |
| 响应 | 已就绪时无额外倒计时、进程启动或发现等待；暂定串口事件解析完成至首条非零发布不超过 100 ms |
| 运动指令 | 持续为前向 0.1 m/s，其余两轴为零，约 50 Hz 发布 |
| 持续时间 | 首条非零发布至首条主动零速发布暂定 3.00±0.05 秒 |
| 实车表现 | 车体向前运动，三秒指令结束后实际停止；通过反馈和现场观察共同确认 |
| 重复操作 | 长按或运动中再点击不续时、不叠加、不排队 |

上述延迟和时间容差是本计划建议的测量口径，实测需保留数值。100 ms 不代表屏幕扫描、物理起步和机械停车的总延迟；停车必须另看实际反馈。软件发零不等于车已物理停稳，发布成功也不证明实际速度精准达到目标。

至少记录按钮原始帧、事件接收时间、首条非零时间、首条零速时间、运动期间指令与实际速度、停止结果及异常原因。连续完成三次独立按下测试后汇总结果。

## 8. 两项验收通过后的正式实现方案

### 8.1 比赛前页面

- 左侧导入现有 `屏幕截图 2026-10-15 220523.png`，等比例缩放并完整保留地图。图片作为屏幕工程资源预装，避免经 9600 波特率串口反复传图。
- 右侧三个按钮分别为“初始启停区”“终止启停区”“一键启动”。前两个按钮每次点击在两个合法区之间切换，并直接在按钮上显示当前选择，起点和终点独立。
- 按地图标识显示“启停区1（节点1）”和“启停区2（节点3）”。现有配置中的 `left` 对应节点1、`right` 对应节点3；不能把地图红色节点编号3误写成“启停区3”。界面优先用地图名称，减少左右视角混淆。
- 点击启动后冻结选择并显示 3、2、1 倒计时；满三秒调用一次 `/mission/start`，收到成功响应并确认比赛运行后进入比赛页面。
- 重复点击不重复倒计时、不重复启动；启动响应不明时先查询状态，不盲目重发。未就绪时显示具体原因，恢复后需要新的点击。

### 8.2 起终点选择如何生效

正式阶段计划给调度增加赛前配置入口，集中校验并应用起点、终点，而不是仅修改屏幕上的文字或写 YAML。

配置入口仅在非比赛运行、执行端静止且无未决动作时接受；更新调度内部起终点并通过既有复位／初始化流程同步规划器起点与朝向。配置完成且回到 READY 后，启动按钮才可用。倒计时开始时再次检查就绪并冻结选择，倒计时结束前复查；异常则取消倒计时并给出原因。

当前只读参数保持“启动初值”的含义，不能把 ROS2 参数设置成功当作运行配置已经改变。运行时的有效起终点及配置结果需通过正式接口回传给屏幕。具体消息和服务在正式阶段实现。

这样初始化在点击启动前完成，避免将“点击后三秒启动”变成“等初始化完成后再倒计时三秒”。比赛当前从开局扫描开始，启动后继续遵循现有总流程。

### 8.3 比赛中持续展示任务码

比赛页使用独立布局：任务码两行大字显示，下方显示抓取、放置累计次数。地图只要求赛前展示，比赛页优先保障任务码和数字可读。

以 `/mission/task_info` 的 `run_id`、`valid` 和 `raw_code` 作为本轮任务码依据，使用匹配的 RELIABLE / TRANSIENT_LOCAL 订阅获取最新快照。`/mission/qr_result` 可辅助观察，但它可能保留上一轮结果，不能脱离本轮有效性直接显示。

扫码前显示“等待扫码”；本轮接受任务码后持续保留至比赛结束，暂停或故障时也不清掉已确认结果。收到正式新轮复位后清除旧轮任务码。屏幕断线重连或重启后，由上位机重新下发当前完整页面数据。

### 8.4 抓取、放置统计口径

显示字段可按需求命名为“抓取正确次数”“放置正确次数”；本项目定义其含义为“对应机构程序已确认执行完成次数”。不等待 `visually_verified`。

| 步骤 `operation` | 累加项 | 包含的业务 |
| --- | --- | --- |
| `PICK` | 抓取 +1 | 原料区取料、粗加工区取回 |
| `PLACE` | 放置 +1 | 粗加工区放料、暂存区平放 |
| `STACK` | 放置 +1 | 第二批暂存码垛 |

沿用调度对 `WorkStepRecord` 的校验：当前轮、当前任务、合法步骤、`controller_completed=true` 才计入。去重键为 `(run_id, task_id, step_id)`；累计反馈、最终结果和重发中出现的同一步骤只计算一次。整批最终失败也保留此前真实完成的步骤数。

每个单物料抓取／放置程序完成后，执行端立即通过现有 Action 的 `confirmed_steps` 反馈；不能等整批三件全部结束才上报。调度提交步骤后立即发布统计快照，屏幕随即更新。快照至少包含本轮身份、抓取数和放置数，并保留最新值供重连恢复。

不能用现有 `confirmed_step_count` 同时代替两种计数，也不在屏幕本地仅凭收到消息次数累加。正式阶段需要从调度账本派生独立统计，使屏幕重连、重复反馈和节点晚加入都不会丢数或翻倍。

按当前两批、每批三件的完整流程，正常完成预期为：

- 抓取：原料区 6 次 + 粗加工区取回 6 次 = **12 次**。
- 放置：粗加工区 6 次 + 暂存平放 3 次 + 码垛 3 次 = **12 次**。

计数从新轮初始化开始为零，暂停、故障或屏幕重连不清零；比赛结束保留最终值，正式新轮复位后才归零。启动前收到旧轮快照时按 `run_id` 丢弃。

### 8.5 正式功能验收

1. 左侧地图完整，三个按钮可用，起终点四种组合均能与调度实际配置一致。
2. 有效启动点击后三秒仅启动一次比赛；未就绪不误启动，重复点击不重复启动。
3. 扫码后任务码持续可见，屏幕重连可恢复本轮结果，新轮不显示旧任务码。
4. 每个已完成抓取／放置步骤及时更新；粗加工区取回及码垛分类正确，重复反馈不重复计数。
5. 完整比赛流程统计为抓取 12、放置 12；中断场景保留中断前的有效完成次数。
