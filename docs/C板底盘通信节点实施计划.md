# C 板底盘通信节点实施计划

日期：2026-10-24  
阶段：需求确认后形成的实施计划；后续已实施首版，使用说明与软件验证结果见 [节点 README](../ros2_ws/src/agv_cboard/README.md)。  
首版目标：让现有 ROS2 底盘速度链路通过 USB CDC 控制真实 C 板，并把真实里程反馈交给现有规划器。

## 1. 已确认需求与范围

本计划依据本次用户确认、仓库现有源码及《上位机通信协议(4).md》编写。原协议中的坐标文字与 C 板实际实现不一致时，以本次确认的实际实现为准。

| 项目 | 已确认约定 |
| --- | --- |
| 协议来源 | 根目录《上位机通信协议(4).md》就是电控提供的协议，C 板已实现 |
| 物理链路 | 使用协议规定的 USB CDC 虚拟串口 |
| C 板位置坐标 | 车辆启动位置为原点；启动时车身左方为 x 正向，前方为 y 正向；位置轴固定于启动参考系 |
| C 板速度字段 | `vx` 向车身左方为正，`vy` 向车身前方为正；是车体系速度，不是启动参考系速度 |
| 角度方向 | `yaw`、`wz` 逆时针为正；`yaw` 保持连续展开 |
| ROS 接口 | 沿用 `/C/controll` 和 `/C/odometry` 及现有消息含义 |
| PC 权限 | 通过 `STATUS.control_source` 判断；非 PC 状态发送全零速度、`mode=0` |
| 遥控规则 | 右拨杆下急停、中 PC、上遥控；遥控器失联停车 |
| 指令超时 | 200 ms 没有新的有效 ROS 速度输入，清除缓存并发送零速；参数可配置 |
| 异常恢复 | USB 断连、C 板重启、遥控接管后清旧速度，不自动续跑原任务 |
| 累计路程 | 同意由上位机累加相邻有效位置距离，不修改 C 板协议 |

首版实现底盘通信、必要状态接收和故障处理。机械臂、龙门架、采放、仓盘、区域同步、ARM_CMD 及其完成反馈均不在本次范围。通信节点不执行路径规划，不发送离散行动码，不自行判断某个比赛任务已完成。

## 2. 现有工程结论

### 2.1 应保持的数据链路

```text
route_planner_node
  └─ /route/control（带任务身份的内部速度与执行状态）
       └─ mission_node 校验与转发
            └─ /C/controll（ControlCommand）
                 └─ cboard_bridge_node
                      └─ USB CDC → C 板 CHASSIS_CMD

C 板 ODOM → cboard_bridge_node
               └─ /C/odometry（OdometryFeedback）→ route_planner_node

C 板 STATUS → cboard_bridge_node
                 └─ PC 权限、底盘故障判断及 /C/status
```

- 比赛运行时，`mission_node` 仍是 `/C/controll` 唯一发布者。
- 通信节点不订阅 `/route/control`，不绕过 mission 的任务校验。
- 不因协议文档中的示例而把主接口改为 `/cmd_vel` 或 `/odom`。
- 不在本次引入标准 TF、定位融合或导航框架。
- 与总体架构文档中较早的“通信待定、离散动作回执”描述冲突时，以当前源码、各包 README 和本计划为准。

### 2.2 累计路程为什么仍有必要

现有 `route_planner_node.py` 的平移控制使用：

```text
本段已走路程 = 当前 total_distance_mm - 本段开始时 total_distance_mm
剩余路程 = 本段目标长度 - 本段已走路程
```

这个值直接决定减速、停车和到达。当前 `OdometryFeedback` 没有二维位置字段，直接去掉累计路程会使现有规划器缺少平移进度，需要另行改造规划与执行逻辑。

“启动点为原点”描述位置；“累计路程”描述走了多远，两者不是同一数据。例如前进 1 m 再后退 1 m，位置回到原点，累计路程是 2 m。不能用到原点的距离代替累计路程。

因此首版保留累计路程，但只把它作为现有规划器的兼容适配，不为此新增线协议字段或下位机功能。未来若规划器改为二维目标位置/方向投影控制，可重新评估并移除这个兼容字段，不在首版同时重构。

## 3. 坐标与单位适配

### 3.1 发送速度

现有 `ControlCommand.msg` 的含义不变：

| ROS 字段 | 含义 | C 板字段 | 转换 |
| --- | --- | --- | --- |
| `vx_mps` | 前进正，m/s | `vy` | 原值写入 |
| `vy_mps` | 左移正，m/s | `vx` | 原值写入 |
| `omega_deg_s` | 逆时针正，°/s | `wz` | 乘以 π/180 |

即：`board_vx = ros_vy`、`board_vy = ros_vx`、`board_wz = radians(ros_omega)`。

这只是对实际协议字段的适配；不得对调后的速度再重复旋转，也不得再次套用原协议描述的 C 板内部麦轮转换。上位机只按 C 板对外实际接受的含义发送。

### 3.2 接收反馈

- 接收到的 `x`、`y` 保留 C 板实际含义：启动时左方、前方的位置，单位 m。
- 接收到的速度 `vx`、`vy` 分别为车身左向、前向，单位 m/s。
- `/C/odometry.yaw_deg = degrees(board_yaw)`，不做角度回绕，不因为交换 x/y 就反转 yaw 符号。
- 累计路程对轴交换不敏感，直接使用实际位置计算相邻位移长度。
- 首版不把 C 板的“x 左、y 前”位置冒充标准 ROS `odom → base_link` 坐标发布。以后要发布 `nav_msgs/Odometry` 或 TF 时，需单独写清位置、姿态及坐标变换。

### 3.3 必须覆盖的方向验收

| ROS 输入 | 预期线协议载荷 | 实车预期 |
| --- | --- | --- |
| 仅 `vx_mps > 0` | `vx=0, vy>0, wz=0` | 前进；初始朝向下位置 y 增大 |
| 仅 `vy_mps > 0` | `vx>0, vy=0, wz=0` | 左移；初始朝向下位置 x 增大 |
| 仅 `omega_deg_s=90` | `vx=0, vy=0, wz≈1.5707963` | 逆时针旋转，连续 yaw 增大 |
| 上述速度取负 | 对应字段取负 | 后退、右移、顺时针旋转 |

车辆转过角度后，再验证速度轴随车体、位置轴仍固定于启动参考系。避免只在初始朝向下测试而漏掉参考系错误。

## 4. 协议实现要求

### 4.1 线格式与处理范围

保留原协议的消息 ID、字节布局、长度和小端序，不自行修改 C 板固件已实现的帧结构。

| 消息 | ID | 负载长度 | 首版处理 |
| --- | --- | --- | --- |
| CHASSIS_CMD | `0x01` | 16 B | 50 Hz 发送，3 个 float32、mode、3 字节零保留位 |
| ODOM | `0x81` | 至少 32 B | 解析位置、连续 yaw、实际速度、时间及状态位 |
| STATUS | `0x82` | 至少 24 B | 解析控制来源、底盘状态、轮在线及错误标志 |
| ACK / ARM_CMD | `0x83` / `0x02` | 见原协议 | 不实现业务逻辑；底盘命令不等待 ACK |

帧格式：`AA 55 + MSG_ID + LEN + PAYLOAD + CRC16`。CRC 覆盖 `MSG_ID + LEN + PAYLOAD`，多项式 `0xA001`、初值 `0xFFFF`、无最终异或、低字节先发；以这些参数为准，不只依据原文的算法名称选择库默认值。

此前已用原文明确的算法核算第 9 节四个示例帧，CRC 均匹配。示例可做字节格式测试，但其中“vx 前向”的文字不能覆盖本次确认的实际方向。

### 4.2 字节流解析与发送

- 支持逐字节、半帧、粘帧、噪声和坏 CRC；不能把一次 USB 读取当成一帧。
- 保留缓冲末尾孤立的 `0xAA`，使跨两次读取的 `AA 55` 能正确拼接。原协议 Python 骨架直接丢弃无完整头的缓冲，不能原样照抄。
- 检查已知消息的最小负载长度；允许按原协议规则忽略追加字段，未知 ID 按完整帧跳过。
- 对损坏 LEN 导致的假半帧设置有界等待和缓冲上限，超时后重新同步；数值属于实现参数，不新增线上字段。
- 校验失败的帧不更新 STATUS/ODOM 新鲜度，不续命 ROS 速度输入。
- 发送端处理短写与写超时；禁止排队补发过期非零速度，串口写故障按链路故障处理。
- 启动、重连时清解析残留和旧命令，避免上一连接的数据进入当前会话。

## 5. 节点与包组织

拟新增 Python ROS2 包 `agv_cboard`，采用与现有工程一致的 `ament_python` 组织方式。串口由一个通信节点独占，协议编解码与业务适配分离。

```text
ros2_ws/src/agv_cboard/
├── package.xml / setup.py / setup.cfg
├── resource/agv_cboard
├── agv_cboard/
│   ├── __init__.py
│   ├── protocol.py           # 编解码、CRC、流式解析；无 ROS/串口副作用
│   ├── transport.py          # USB CDC 打开、读取、写入、重连
│   ├── chassis_adapter.py    # 坐标单位、里程累计、命令有效期及权限状态
│   ├── command_executor.py   # 保留 Humble DDS 发送时间，过滤积压速度
│   └── cboard_bridge_node.py # ROS 接口与定时发送
├── config/cboard.yaml
├── launch/cboard.launch.py
├── udev/99-rm-cboard.rules   # 安装示例，真实 VID/PID/序列号现场确认
└── README.md
```

依赖优先使用现有 ROS2 Humble、`rclpy`、`agv_interfaces`、`std_srvs` 和 `python3-serial`。不在方案阶段安装依赖或修改系统 udev。

串口读取不得阻塞 ROS 回调和 50 Hz 发送。实施时采用一个有超时的串口 I/O 工作循环，ROS 回调只交接最新命令；共享状态用明确的串行访问或锁保护。循环错过周期时不突发补发积压命令。

### 5.1 ROS 接口

| 接口 | 类型 | 用途 |
| --- | --- | --- |
| 订阅 `/C/controll` | 现有 `agv_interfaces/msg/ControlCommand` | 唯一 ROS 速度输入，保留前/左语义 |
| 发布 `/C/odometry` | 现有 `agv_interfaces/msg/OdometryFeedback` | 有效累计路程 mm、连续角度 ° |
| 发布 `/C/status` | 拟新增 `agv_interfaces/msg/CBoardStatus` | 链路、权限、故障及反馈健康情况 |
| 服务 `/C/reset_fault` | `std_srvs/srv/Trigger` | 显式清除通信侧运动故障锁；不恢复路线、不复位 C 板位置 |

`CBoardStatus` 拟包含 ROS 接收时间、是否连接、STATUS/ODOM 是否新鲜、实际控制源、底盘状态、在线位图、错误位、ODOM 状态位、板端原始时间、是否允许运动及禁止原因。无有效板端数据时必须带有效性标志，不能把初始化的零字段报告为真实健康状态；板端来源与上位机判断分别保留。

首版通过状态消息和节流日志定位故障；不把尚未定义的机构字段做成控制功能，不引入机构 Action/Service。

### 5.2 配置初稿

| 参数 | 计划值 | 说明 |
| --- | --- | --- |
| `serial_port` | `/dev/rm_cboard` | 稳定设备链接，禁止依赖 ACM 编号 |
| `send_rate_hz` | 50.0 | 与已实现协议一致 |
| `command_timeout_s` | 0.2 | 用户已同意；只由新有效 ROS 输入刷新 |
| `status_timeout_s` | 0.2 | 设计初值，针对 20 Hz STATUS，实机核对 |
| `odometry_timeout_s` | 0.2 | 设计初值，针对 100 Hz ODOM，实机核对 |
| `reconnect_interval_s` | 1.0 | 设计初值，只重连链路，不恢复任务 |
| `control_topic` / `odometry_topic` / `status_topic` | 上表话题 | 启动时读取，可配置 |

未得到实际线材枚举信息、底盘噪声和速度能力前，不编造 VID/PID 唯一匹配条件、位置突跳阈值、里程死区或实车速度上限。计划值与已确认协议常量必须在说明中区分。

## 6. 权限、停车与恢复

### 6.1 每次发送都重新判定

只有连接有效、STATUS 新鲜且 `control_source=2`、ODOM 有效新鲜、底盘无禁止运动故障、无恢复锁，并且收到新的有效 ROS 命令时，才允许发送非零速度。

- PC 正常且命令有效：按最新速度发送 `mode=1`；零速输入统一发送全零、`mode=0`。
- 未收到任何状态、控制源未知、控制源非 PC、状态过期或输入过期：发送全零、`mode=0`，清除旧非零命令。
- 非 PC 期间接收到的非零 ROS 输入不得缓存到将来的 PC 会话。恢复 PC 后只接受权限恢复之后的新输入。
- 200 ms ROS 指令看门狗使用本机单调时间；50 Hz 串口重发本身不能延长输入有效期。
- 拒绝 NaN、Inf 和无法编码为有限 float32 的速度；收到非法输入时清缓存并归零，不能静默保留上一条非零速度。
- 遥控急停及 C 板自身保护仍在下位机生效；上位机发零不表示撤销遥控权限，也不等于物理急停或已停稳证明。

### 6.2 底盘状态处理

- 四轮离线、急停、CAN 发送异常和 IMU 故障列入运动禁止条件。
- ODOM 的 `odom_valid`、`imu_ok`、`enc_ok` 与打滑位用于有效性判断；无效、故障或打滑期间不累计、不伪造健康反馈。
- 仅机构相关的状态字段保留原始值，首版不实现机构动作，不笼统把任何机构位都解释为底盘故障。
- `chassis_status=disabled` 或 `input_timeout` 不能简单形成“永远不再发有效指令”的循环：健康 PC 状态下，空闲停止和输入超时恢复的许可依协议区分；断开/过期/真实故障仍须经过恢复流程。

### 6.3 不自动续跑原任务

首次启动等待就绪与运行中故障区分处理。运行期间出现链路中断、板端复位、反馈失效或失去 PC 权限时：

1. 清速度缓存，连接可写时尽力发全零 `mode=0`，记录原因并锁住非零输出。
2. `/C/status` 持续报告故障；暂停发布“可用于执行”的 `/C/odometry`，不能拿最后一帧重复发布让规划器误认为健康。
3. 现有规划器会因里程超时中止路线，mission 随后停止转发；不能把收到新的速度流当成故障已恢复。
4. 链路、PC 权限和新反馈恢复后，保持锁定，直到人工按现有流程停止/复位任务并调用 `/C/reset_fault`。
5. 清锁服务至少检查 STATUS/ODOM 新鲜且健康、PC 权限成立、最新 ROS 输入为新鲜零速；服务成功后仍保持零速，只接受之后的新命令。服务不宣称车辆位置已经恢复，也不自动调用规划服务。

现有规划器的 `odometry_timeout_s` 为 0.5 s，故障后底盘桥接侧先归零，规划器在其既有超时内中止。桥接停止输出时不应把“已发零命令”称为物理静止。首版不为追求立即联动而重构 mission；若实机发现现有超时不够，单独评估 `/C/status` 对规划器的最小接入。

正常关闭时尽力发送零速并关闭串口；进程被强杀或链路已断时依靠 C 板既有 200 ms 输入超时停车，不能声称退出回调一定执行。

## 7. 里程、时间与重启

### 7.1 累计方法

首个有效 ODOM 只建立位置基线，累计值从 0 开始。后续连续有效样本采用：

```text
delta_mm = 1000 × hypot(x_now - x_prev, y_now - y_prev)
total_distance_mm += delta_mm
yaw_deg = yaw_rad × 180 / π
```

- 不使用 `hypot(x, y)` 代替累计路程，不积分指令速度制造“已走路程”。
- 前进、后退、左右平移均累计正路程；旋转进度仍由现有规划器使用连续 yaw 判断。
- 同一板端 ODOM 时间戳的重复样本不重复计数，不更新健康时间。
- 首版不为“看起来更平稳”擅自设置滤波、位置死区或速度门限；先测静止噪声、原地旋转漂移和直线误差，再决定是否需要。
- 相邻位置连线在丢帧或弯曲运动时可能低估真实路径，位置抖动则会高估。首版适用于现有逐段平移控制，不承诺其达到当前 5 mm 到达容差所需的实车精度。

### 7.2 时间使用

- 板端 `t_ms` 用于样本顺序、采样间隔及回绕检测；STATUS 与 ODOM 分别维护序列状态，不能因不同周期交叉到达就误判回退。
- ROS 消息 `header.stamp` 首版使用本机接收时的 ROS 时间；通信超时使用单调时间。
- 不把“上电经过的毫秒数”直接当成 ROS 绝对时间。原协议示例中“用 t_ms 换算 stamp”缺少时钟对齐细节，首版不增加时钟同步协议。
- 序号比较按 uint32 模运算处理正常回绕；无序列号/启动身份的协议不能仅靠 t_ms 绝对可靠地区分所有复位情况，需结合 USB 重连、时间不连续和位置突变保守判断。

### 7.3 失联、复位与跨轮

- 不跨异常间隔累加位置差，不把 C 板位置归零当成一次长距离运动。
- 确认或怀疑新里程会话后停止累计并锁住运动，重新建立基线须与人工恢复及规划器复位配合。
- 通信节点重启会丢失上位机累计值；必须先停止任务、恢复已知场地状态，再复位规划器上下文。不能在执行中静默归零或平滑拼接后继续旧任务。
- 一轮比赛的软件复位不要求重置 C 板坐标原点；现有规划器每段取基线，并在 `reset_context` 清理旧累计检查和 yaw 基准。
- 首版不发送 POSE_SET，不修改已实现的 ODOM 帧。涉及板端重启但没有 USB 事件的不可判定情况，在实机验收记录中明确能力边界。

## 8. 实施顺序与交付

## 9. 验收清单

### 9.1 无运动验证

- 编解码与原协议四个示例 CRC 匹配；收帧处理任意切分、孤立 AA、粘帧、坏 LEN、坏 CRC、未知 ID 和追加字段。
- 使用内存输入或伪终端验证，不产生比赛模拟成功，不恢复已清理的模拟比赛入口。
- 未收到 STATUS、非 PC、无 ROS 输入、输入超时和非法速度时，输出为全零 `mode=0`。
- 验证命令以 50 Hz 发出，但超过 200 ms 不再重发旧非零速度。
- 验证状态失效、ODOM 冻结、重复 t_ms、正常回绕、重启和短写，均不制造健康里程或错误累计。

### 9.2 实车低速验证

在受控场地低速逐项测试，比赛调度与独立命令发布不得同时控制 `/C/controll`。

1. 确认真实 USB 枚举标识及稳定设备链接；多块相同设备不能只凭通用 VID/PID 区分。
2. 验证前、后、左、右和双向旋转；转过 90° 后复测车体系速度与固定位置轴。
3. 验证 90°/180°及跨 ±π 连续角，不做角度回绕。
4. 验证已知距离往返：位置返回原点附近，累计路程仍增长；测静止和原地转向的虚增。
5. 停止 ROS 输入、结束通信进程、拔掉 USB、复位 C 板，分别测实际停车延迟。200 ms 为看门狗阈值，不是保证物理停稳时间。
6. 切遥控/PC/急停，验证控制源上报、PC 零帧不会抢夺遥控权限，恢复 PC 后不续跑旧任务。
7. 在现有规划器下测试短距离平移、减速和到达；不因软件完成标志就宣称实车达到 5 mm 精度。

### 9.3 本次尚未实测的事实

没有在本次需求分析中连接 C 板、验证已刷固件的字节流、安装 udev、启动 ROS 控车或测量底盘运动。C 板实现进度和轴定义来自用户确认。实机枚举标识、实际采样频率、状态位行为、反馈噪声及速度能力在实施联调中记录，不作为未经测量的既定结果。
