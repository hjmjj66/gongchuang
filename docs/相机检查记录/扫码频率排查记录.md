历史记录：保留排查结论；下文性能检查脚本已在实车目录清理时删除，相关命令不再作为运行入口。

2026-10-15，RDK X5 / OpenCV 4.11 / ROS2 Humble，使用当前 USB 相机、640×480、关闭预览。

## 本次实测

- 从正在运行的 `/qr_node` 读取到 `scan_rate_hz: 10.0`、`camera_fps: 30.0`、`show_preview: false`。
- 对原节点短时执行 `ros2 topic hz /qr/center`，曾测到 9.139 Hz 和 9.997 Hz；随后被动观测 22 秒，两个话题均为 0 消息。因此发布并非始终只有几 Hz，也存在无法成功解码的时段。
- 经用户同意，临时停原节点，使用同一算法、同一 YAML 运行 30 秒，只打印耗时，不添加业务话题。

## 可以确认的原因与限制

1. 当前配置将扫描频率设为 10 Hz，并不对全部相机帧执行解码。
2. 只有成功解码的处理帧才发布。若扫描为 10 Hz、成功率为 30%，输出约为 3 Hz。禁止识别失败时重发旧结果的需求保持不变。
3. 为保证选择原图中面积最大的可解码二维码，当前代码会遍历候选四边形。每个候选都透视到 500×500 再调用 ZBar，是主要耗时。复杂场景可能使扫描本身低于 10 Hz；本次稳定窗口仍达到约 10 Hz。
4. 本次 30 秒没有成功解码，尚未检查当时画面，因此不能据此断定是二维码尺寸、距离、反光、失焦、运动模糊还是算法候选提取失败。
5. 本地订阅曾收到约 10 Hz，当前证据不支持把现象归因于 Foxglove；未专门验证电脑链路丢包。

## 诊断工具

`tools/profile_qr_node.py` 不修改生产算法；运行时会独占相机，需要先停止原扫码节点。

```bash
source /opt/ros/humble/setup.bash
source /root/工创/ros2_ws/install/setup.bash
python3 /root/工创/ros2_ws/tools/profile_qr_node.py --duration 30
```

每 5 秒打印实际采集 Hz、处理 Hz、成功发布 Hz、成功率、每帧平均/P95 耗时和各步骤耗时。测试结束后按 README 中的 launch 命令恢复节点。

本次未修改算法、扫描频率、相机控制、输出接口或发布规则。新增的只有诊断工具和此记录。
