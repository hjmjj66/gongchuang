# 扫码相机与处理频率优化

历史记录：保留参数与性能结论；下文诊断工具和原始日志已在实车目录清理时删除。

日期：2026-10-20。设备：RDK X5 / DH USB2.0（05a3:9230）/ OpenCV 4.11.0 / ROS2 Humble。640×480、MJPEG、关闭预览。C100 保持连接，但没有同时取流。

## 结果

已修改源码、源码 YAML，并重新构建 `agv_perception`，常规 ROS2 启动命令将使用新版。两个业务话题、消息格式、原图中心坐标计算、选取最大可解码二维码及失败不发布规则保持原样。没有修改方法三的图像处理和识别算法。

使用相同诊断工具 `ros2_ws/tools/profile_qr_node.py`，优化前运行 20 秒，优化后运行 25 秒，每 5 秒输出计数。首个窗口包含约 2 秒初始化，不用于稳定性能比较。

| 项目 | 优化前稳定窗口 | 优化后稳定窗口 |
| --- | --- | --- |
| 相机采集 | 19.88～20.13 fps | 29.80～30.00 fps |
| 二维码算法处理 | 14.98～15.01 Hz | 29.01～29.60 Hz |
| 每帧算法平均耗时 | 30.5～35.1 ms | 28.9～29.0 ms |
| CPU 使用率（100% 为一核） | 103%～122% | 189%～191% |
| 成功解码及发布 | 本次视野为 0 | 本次视野为 0 |

算法处理速度约为原来的两倍；发布频率还取决于二维码能否被识别。本次现场未成功解码，不能声称真实二维码已达到每秒 30 次成功识别。额外用 OpenCV 生成 `123+321` 二维码，直接调用原解码器验证文本和原图中心坐标，结果通过；该验证不能代替实拍二维码效果检查。

## 改动

- `camera.py`：V4L2 缓冲默认从 1 改为 4，继续使用独立线程持续采集、只保留最新帧。
- `camera.py`：连接时通过标准 V4L2 控制配置 `exposure_dynamic_framerate`，默认关闭；保持自动曝光。读取相机原值并在每次断开、读取失败或正常退出后恢复；不支持这个控制时记录警告并继续采集，不因缺少该控制陷入重连。
- `qr_node.py` / `qr.yaml`：新增 `camera_buffer_size: 4`、`camera_dynamic_framerate: false`；目标 `scan_rate_hz` 从源码 YAML 的 15 提高至 30，节点不带 YAML 的默认值也统一为 30。
- `README.md`：更新参数、性能及暗光画质和处理频率说明。

相机原 `exposure_dynamic_framerate` 为 1，运行时临时设置为 0，优化后实机程序退出再次读取为 1；`auto_exposure` 始终为 3。没有强制固定曝光，没有更新固件或设置系统级开机控制。

## 验证与限制

- 包构建成功。
- 新增 5 项相机控制与清理测试：控制文件描述符失败关闭、原值读取及设置、正常停止恢复、读取失败恢复、不支持控制时继续输出图像，全部通过。
- 真实相机运行 25 秒，稳定采集约 30 fps、算法处理约 29～29.6 Hz，未出现采集失败或恢复警告。
- 生成二维码文本与中心坐标检查通过。
- 所有检查程序结束后已释放相机，没有留下后台扫码进程。

处理频率提高意味着 CPU 消耗增加；当前算法每帧约需 29 ms，已经接近 30 Hz 的 33.33 ms 时间预算。复杂背景、多候选四边形、实际二维码或其他视觉模块并行运行时，性能可能降低，需要在最终工作画面下实测。关闭动态帧率在暗光下也需检查亮度、噪声和运动模糊。四缓冲改善吞吐，未实测端到端图像时延。
