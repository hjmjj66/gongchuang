# C 板通信与二维里程反馈改造计划

编写日期：2026-10-25。状态：需求已确认，软件已按本计划实施并完成构建及自动化验证；实车验收尚未执行。计划编写时仅新增文档，后续实施结果见 [改造实施记录](C板通信与二维里程反馈改造实施记录.md)。

本文覆盖 C 板通信、二维里程反馈、路线执行、mission 转发、浏览器调试工具，以及相关测试和文档的整体迁移。与旧文档冲突时，以本文记录的本轮需求为准；实施时同步更新旧文档，不能只留下互相矛盾的说明。

## 1. 已确认的需求与范围

### 1.1 接口和坐标约定

1. `/C/controll` 保留现有拼写，是上位机希望下位机执行的速度输入话题，通信节点订阅并向串口转发。
2. 所有项目内速度输入统一为车体系：`vx_mps` 向当前车头前方为正，`vy_mps` 向当前车身左侧为正，`omega_deg_s` 逆时针为正。转向后指令方向随车身改变。
3. `/C/odometry` 提供 `x_m`、`y_m`、`yaw_rad`、`yaw_deg`、`vx_mps`、`vy_mps`、`wz_rad_s`，移除 `total_distance_mm`；允许增加时间、有效性及坐标版本等元信息。
4. 位置属于本次建立的固定里程坐标系：原点为重置时的车辆位置，+x 为当时车头前方，+y 为当时车辆左侧。车辆运动、转向后，位置坐标轴保持固定。
5. 里程反馈中的 `vx_mps`、`vy_mps` 是下位机上报的当前车体系实际速度，不是位置坐标系速度，也不是输入指令的回显。
6. `yaw_rad`、`yaw_deg` 表示相对于本次原点朝向的连续底盘航向；两者只差单位，逆时针为正，不做 ±180° 或 0～360° 回绕。
7. 每次进入 PC 控制、通信节点重启、串口重新连接或检测到板端重启，都重新建立原点、坐标轴和航向零点。
8. `/C/chassis_odometry` 继续保留下位机原始位置、航向、速度和状态，作为原始观测与排查依据。

### 1.2 运行行为

1. `command_timeout_s` 默认改为 `0.05`，写入 C 板 YAML 参数；输入停止后不无限维持最后一条非零速度。
2. 串口仍按 50 Hz 周期发送，无新鲜有效输入或当前不允许运动时发送全零速度、`mode=0`。
3. 里程观测与 PC 运动许可分离：遥控、PC、停止或可解析但健康异常时，都可发布新收到的观测；不因为禁止 PC 运动而停止位置观测。
4. 故障和控制权恢复后，通信节点自动恢复接收新指令，无需人工调用清锁服务；不恢复缓存的旧非零指令。
5. 旧路线遇到控制权丢失、原点重置或执行所需反馈异常时终止；恢复通信不恢复旧路线。
6. 调试中遇到重置，需要重新选择当前位置、朝向等信息，再点击“开始”，形成一次新的任务初始化。
7. 正式比赛中，用户先将车放在配置起点、摆正朝向，再切 PC 建立原点；比赛中不切遥控、不手动接管。异常时仍应停止旧任务。

### 1.3 本次选择 A 方案

- 路线平移进度根据起点、固定目标方向和当前 x/y 的有符号投影计算。
- 保留现有拓扑路线、动作合并、分段执行、减速和停车策略。
- 横向偏移、反向位移、原地旋转不能被累计成有效前进。
- 本次不加入自动横向纠偏、平移锁头、二维目标位置收敛或 PID 调参。
- B 方案，即二维位置与航向闭环，作为后续独立改进记录，不能在本次实施中悄悄扩大范围。

## 2. 当前实现的问题与判断边界

| 现象 | 代码中已确认的情况 | 本轮处理 |
| --- | --- | --- |
| `/C/controll` 无输入就不更新 | 目前它只有订阅端，不由通信节点补发；串口线程已有周期发送 | 保持输入话题职责，在串口验证空闲零速，不向输入话题自发零速 |
| `/C/odometry` 只有累计路程和 yaw | `OdometryFeedback.msg` 为旧规划器反馈契约 | 替换为二维反馈，并同步迁移所有消费者 |
| 切 RC 后反馈停止、切回 PC 仍锁住 | `update()` 把非 PC 状态锁存为故障，里程发布又依赖运动许可 | 分离观测与许可，改为当前健康判定与自动恢复 |
| `fault_reason` 一直显示旧控制权原因 | 当前优先返回锁存的 `adapter.fault` | 当前原因随状态变化更新，历史信息只进入日志 |
| 静止时两个底盘话题的 yaw 同时减小 | 两者使用同一下位机 yaw，上位机没有航向积分，仅做单位换算 | 保留原始数据，提供静止采样与对比，向电控提供证据 |
| 三秒命令看起来只运动一秒 | 尚未取得现场连续日志；CLI 启动和 DDS 发现也占用外部 timeout 的时长 | 分别记录发布、接收、下发和反馈，采用连接完成后计时的测试 |

`/C/status.yaw_rad` 是机构 YAW 轴反馈，不是底盘航向，一直为零不能证明底盘 IMU 正常。

当前证据指向“下位机上报的底盘航向在漂移”，但尚不能确定是陀螺零偏、标定、融合、振动还是其他原因。没有下位机源码和静止原始采样时，不宣称已定位具体电控缺陷；本轮不通过上位机减去线性漂移来掩盖问题。

## 3. ROS 接口迁移

### 3.1 `ControlCommand.msg`

保留三个主要速度字段，修改注释与所有生产者的轴含义：

```text
float64 vx_mps       # 当前车头向前为正，m/s
float64 vy_mps       # 当前车身向左为正，m/s
float64 omega_deg_s  # 逆时针为正，deg/s
```

路线控制链需要携带来源坐标和本次运动许可的标识，防止自动恢复时尚未收到中止通知的旧规划器继续发送“时间新鲜、任务已过期”的指令。计划增加可选元信息：

```text
string odom_session_id  # 自动任务绑定的坐标会话；手工速度输入可留空
uint64 motion_epoch    # 自动任务绑定的运动许可代次
```

约定：

- 规划器生成的任务指令必须绑定当前坐标会话与运动许可代次；mission、调试工具原样转发。
- 通信节点拒绝绑定旧坐标或旧许可代次的非零指令，即使该消息刚刚发布。
- 直接用 CLI 发送的无绑定指令继续支持，必须满足 PC 权限、健康、新鲜度及恢复后的时间门槛。
- 全零指令始终可用于表达停止，但不能使反馈异常恢复、建立原点或延长其他非零命令的有效期。
- `motion_epoch` 是解决故障恢复与异步任务中止之间竞态的内部元信息，不改变速度语义，不增加用户手动操作步骤。

### 3.2 `OdometryFeedback.msg`

计划字段：

```text
std_msgs/Header header
string odom_session_id
uint64 motion_epoch
uint32 board_time_ms
uint8 odom_status
bool origin_initialized
bool valid

float64 x_m
float64 y_m
float64 yaw_rad
float64 yaw_deg
float64 vx_mps
float64 vy_mps
float64 wz_rad_s
```

- 删除 `total_distance_mm`，不保留兼容累计里程，不在消费者内部重新累加相邻点路程冒充迁移。
- `header.stamp` 近似本地收到该帧的时刻，不把旧采样重新盖章为新数据；`header.frame_id` 标明本次固定里程坐标系。
- `odom_session_id` 使用跨进程重启不会复用的标识，每次请求重建坐标时更新。原点尚未初始化时也能用它通知消费者当前会话已变化。
- `origin_initialized=false` 时，数值字段不得作为已建立的局部坐标使用；原始值可从 `/C/chassis_odometry` 读取。
- `valid` 表示当前采样及原点是否有效，不表示允许 PC 控制；RC 模式也可以有有效里程。
- `motion_epoch` 与状态中的许可代次一致，用于任务绑定和异常检测。
- `vx_mps`、`vy_mps`、`wz_rad_s` 直接来自下位机观测，不用指令代替实际速度。如果板端速度长期为零而位置变化，应明确报告给电控。

### 3.3 `CBoardOdometry.msg` 与原始观测

保留 `/C/chassis_odometry` 的原始语义和现有字段，不在其中减原点、旋转位置或减 yaw 零点。更新说明，明确它与 `/C/odometry` 的差异为“板端原始坐标 / 上位机本次会话坐标”，不再是“诊断观测 / PC 才能获得的执行反馈”。

健康异常但数值可解析的原始新帧仍发布 `valid=false`；串口断开或没有新帧时不重放旧值。

### 3.4 `CBoardStatus.msg`

保留连接、板端状态和健康信息，调整注释与语义，并增加：

- `odom_session_id`、`motion_epoch`、`origin_initialized`：与反馈和自动指令绑定使用。
- `command_fresh`：是否存在可用的新鲜速度输入。
- `command_age_s`：最近输入的源年龄，无输入时使用约定的负值；不使用零伪装“刚收到”。
- `command_reason`：当前为什么发送零速或拒绝指令，例如无输入、输入超时、旧任务绑定、来源时间异常。

`fault_reason` 只描述当前通信/控制许可问题。RC 时报告当前非 PC 状态，切 PC 后若其他条件健康则自然清空；若还有其他问题则显示新问题。正常待命的零速或普通输入超时放在 `command_reason`，不永久污染故障字段。

`motion_allowed` 表示反馈、原点及权限就绪，可接收匹配的新指令；它与 `command_fresh` 分开，也不代表车辆已物理停稳。

### 3.5 路线相关接口

`RouteExecutionProgress.msg`：

- 删除 `baseline_distance_mm`、表示实测累计路程的 `total_distance_mm`。
- 增加坐标会话、许可代次、本段起点 x/y、当前 x/y、目标单位方向、纵向投影进度及横向偏差。
- 保留任务/进程身份、合并段编号、opcode、起终节点、目标量、yaw 基线和当前 yaw。
- `progress` 的单位继续随段类型：平移为 mm，旋转为 deg，必须在接口注释中写清。

`ExecutorRuntime.msg`：增加里程坐标会话和许可代次，供 mission 与调试工具确认执行上下文是否仍有效。

`RouteControl.msg`：继续嵌套 `ControlCommand`，利用其中的会话绑定，不重复创建另一套不一致的字段。

`RoutePlan.total_distance_mm` 与 `planner.py` 中的同名字段表示拓扑规划路径长度，不是实测累计里程，保留。逐边长度、动作目标距离、减速距离也继续使用 mm，不因删除反馈字段而误删。

### 3.6 `/C/reset_fault` 的处理

通信节点不再依赖人工清锁。为避免存量脚本立即失去服务，计划暂时保留该服务作为幂等的当前健康检查兼容入口，返回“自动恢复已启用”及当前就绪结果；它不再清锁、不强行允许运动、不重置坐标、不恢复路线。

调试工具取消对该服务的就绪依赖和恢复调用，文档删除“先发零速再手动清锁才能继续”的旧操作要求。后续独立清理版本再考虑移除兼容服务。

## 4. 坐标建立与变换

### 4.1 前 x、左 y 下的旋转公式

按 2026-10-26 实车确认的 x 前、y 左和 yaw 逆时针约定，车体系向固定系转换为：

```text
M(theta) = [ cos(theta)  -sin(theta)]
           [ sin(theta)   cos(theta)]

v_fixed = M(theta) * v_body
```

因此，初始朝向逆时针转 90° 后，沿当前车头前进应增加固定系 y，固定系 x 约不变。

### 4.2 原点变换

首次满足条件的板端样本记为 `(x0, y0, yaw0)`，之后每条板端原始样本 `(xb, yb, yawb)` 转换为：

```text
dx = xb - x0
dy = yb - y0
c = cos(yaw0)
s = sin(yaw0)

x_m = c * dx + s * dy
y_m = -s * dx + c * dy
yaw_rad = yawb - yaw0
yaw_deg = yaw_rad * 180 / pi
```

`vx_mps`、`vy_mps` 保持当前车体系速度，不随固定坐标重建旋转；`wz_rad_s` 保持原始逆时针角速度。

新会话第一条有效反馈的位置、航向为零，速度可以非零：若切换时车辆仍在运动，不能为了显示归零而伪造实际速度为零。

### 4.3 原点建立条件与复位事件

| 事件 | 坐标处理 | 指令和任务处理 |
| --- | --- | --- |
| 节点启动，已经是 PC | 建立新会话，等待切入后第一条健康新 ODOM 建原点 | 不接收启动前积压速度；等待新指令 |
| 节点启动，处于 RC | 原点未建立，继续原始观测；进入 PC 后建原点 | 持续向板端发零速 PC 帧 |
| 非 PC → PC | 新建坐标会话，以切入后第一条健康新 ODOM 建原点 | 清旧速度，终止旧任务，重新初始化地图上下文 |
| PC → 非 PC | 保留上一坐标系继续观测 | 立即撤销 PC 许可、清速度、通知任务中止 |
| 串口断开后重连 | 新建坐标会话，即使板端计数没有归零也重新建原点 | 自动恢复通信，旧任务不恢复 |
| 检测到板端重启 | 原点失效，新建会话，等待新反馈建原点 | 清速度和旧任务，健康恢复后接受新任务 |
| 短时健康异常后恢复，板端坐标连续 | 保留现有坐标会话和原点 | 更新许可代次、清旧速度，中止旧自动任务后可接收新任务 |
| 用户点击调试“开始/复位” | 只建立地图锚定和任务上下文，不额外重置板端或通信里程原点 | 创建新任务身份并绑定当前坐标会话 |

原点建立必须使用重置事件之后收到的新有效样本，不能用切换前缓存的最后一帧。不为坐标复位新增下位机命令；现有协议没有可用的位姿设置帧，本次在上位机变换。

断连、重连与 PC 状态确认可能属于同一次恢复过程：用一个“等待原点”的事务合并初始化，不因 STATUS 每次仍为 2 或多个定时器反复归零。真正再次发生进入 PC/重连/重启时仍生成新会话。

板端时间戳回退不能直接等同每一条旧帧都是重启：保留 uint32 自然回绕、去重和乱序处理，使用两类帧及后续时间演进确认新时间基线。不能在 STATUS、ODOM 交错到达时重复重建坐标。对疑似重启先停止运动，待确认新样本后自动恢复；仅有时间戳的协议无法无歧义识别所有“快速重启且时间已经追平”的情况，这一限制需在诊断中保留。

## 5. 通信、超时与自动恢复

### 5.1 参数

```yaml
cboard_bridge_node:
  ros__parameters:
    send_rate_hz: 50.0
    command_timeout_s: 0.05
    status_timeout_s: 0.2
    odometry_timeout_s: 0.2
    reconnect_interval_s: 1.0
```

除明确要求的速度输入超时外，不擅自缩短反馈超时或改动用户当前规划速度、减速区与容差。参数仍在启动时读取，并在启动日志/调试显示中标明实际加载值。

### 5.2 串口速度发送

发送非零速度需要同时满足：连接正常、STATUS 新鲜、PC 控制、轮在线、相关错误位正常、ODOM 新鲜健康、原点已建立、指令新鲜、来源时序有效、任务绑定匹配。

对应 C 板实际轴约定：

```text
board_vx = command.vx_mps
board_vy = command.vy_mps
board_wz = radians(command.omega_deg_s)
```

ROS 与协议均为 forward/left，桥接不交换轴，也不额外取反。

任何条件不满足或收到零速时，持续发送 `(0,0,0,mode=0)`。不将这种内部兜底发送再次发布到 `/C/controll`，避免节点订阅自己产生的零速并覆盖上游控制。

0.05 秒以消息实际源时间判断有效性，不因为串口重发延长。保留当前 DDS 源时间检查、防乱序和防积压设计，针对 ROS2 Humble 的 `CommandExecutor` 做回归，而不是通过放弃时间检查解决一秒停车问题。

50 Hz 发送周期为 20 ms，因此最后一条输入超过 50 ms 后，在下一次实际发送周期归零；调度正常时观察到的串口零速时刻约在最后输入后的 50～70 ms，而非保证精确在 50 ms。反馈异常、控制权丢失、串口故障仍可提前触发零速。

### 5.3 当前健康状态替代故障锁存

- 将原有 `fault` 锁存路径改为当前状态判定；原因消失时清除，原因改变时更新。
- 健康/许可失效时立刻清除缓存命令，推进运动许可代次，使旧自动指令失效；恢复时设置新的指令时间门槛。
- 重连、切 PC、建立原点后，只接收该次恢复门槛之后发布的新鲜非零指令。
- 历史故障以事件日志记录，当前 `fault_reason` 不承担历史记录职责。
- `/C/status` 保持周期更新，并及时传递会话、许可代次变化；即使消费者没观察到极短的异常状态，也可通过代次变化终止旧任务。
- 无输入属于正常待命；输入超时触发零速但不要求复位。健康恢复也不要求人为先发一次零速。

### 5.4 观测发布与运动许可分离

解析、原始观测更新、会话坐标变换、运动许可、ROS 发布分别处理。不能再以 `adapter.update()` 返回允许运动作为是否发布 ODOM 的条件。

- 新解析的 ODOM 可在 RC 下更新原始和已初始化的会话坐标。
- 健康位异常但结构、数值合法时发布无效观测，供调试使用；消费者依据 `valid` 停止执行。
- CRC 错误、数值非有限、重复板端时间或无新帧时不生成“新里程”。
- 断连时状态持续报告断连，里程话题不靠重放旧值维持频率；消费者同时检查消息时间与状态。
- ROS 发布继续放在 ROS 执行器内，串口 I/O 保持独立，避免 DDS 阻塞影响 50 Hz 发包。

## 6. 路线执行从累计路程迁移到二维投影

### 6.1 控制轴映射

| 动作 | vx 符号 | vy 符号 | omega |
| --- | --- | --- | --- |
| 前进 | + | 0 | 0 |
| 后退 | - | 0 | 0 |
| 左移 | 0 | + | 0 |
| 右移 | 0 | - | 0 |
| 左转 | 0 | 0 | + |
| 右转 | 0 | 0 | - |

规划器、所有测试/模拟器、调试工具和未来视觉文档采用同一约定，mission 只校验转发，不再交换轴。

### 6.2 本段基线和有符号进度

每段平移开始记录：坐标会话、许可代次、`p_start=(x_start,y_start)`、`yaw_start`、opcode 和目标长度 `L_mm`。

opcode 对应车体系单位方向 `b=(bx,by)`，按上一表取值；本段固定目标单位方向为：

```text
e = M(yaw_start) * b
delta = (x_now - x_start, y_now - y_start)

signed_progress_mm = 1000 * dot(delta, e)
cross_track_mm = 1000 * (e.x * delta.y - e.y * delta.x)
remaining_mm = L_mm - signed_progress_mm
```

目标方向只在本段开始时确定，不随每一帧 yaw 改变，否则航向漂移会使任务目标方向也随车漂移。

`signed_progress_mm` 保留符号供判断；显示/减速计算按需要使用非负进度，但不能把负方向运动取绝对值变成前进。短时噪声允许在合理阈值内波动，不沿用“累计路程永远不下降”的检查；无进展超时使用目标方向上的实际最佳推进，不让往复抖动反复续命。

### 6.3 到达、减速与异常

- 继续使用当前 `ramp_speed()`、段目标长度与 `translation_arrival_tolerance_mm`，按纵向投影剩余量减速、到达后发送零速。
- 横向偏差单独输出到诊断和界面，本轮不自动纠偏，也不将“纵向投影达到”宣传成二维位置已精确到达。
- 不新增未经确认的横向故障阈值或航向闭环；现有超时、健康检查和新会话/许可变更可中止任务。
- 不额外实现反向补偿越过的目标；保留现有越过纵向到达门槛即停车的行为。
- 转向继续比较连续相对 yaw，旋转期间 x/y 漂移不计成任何后续平移进度。
- 本次不改变当前配置中的快慢速、5 mm 到达容差、转向容差等数值。软件阈值不等于物理停车精度，需单独记录实车误差。

### 6.4 删除旧反馈状态

移除 `_distance_mm`、`_last_distance`、累计值回退故障、每段累计距离基线等依赖，替换为当前位置、段起点、方向投影和会话/许可绑定。起点与当前点的欧氏距离也不能作为通用替代，否则横向走偏仍会被计为进度。

拓扑最短路、各道路长度、路径总长度和路线动作合并继续保留。不得通过全局搜索替换，把计划中的距离和实测累计里程混为一谈。

## 7. 坐标复位与任务生命周期

### 7.1 规划器

- 订阅反馈和 C 板状态，及时识别非 PC、反馈异常、原点变化和许可代次变化。
- 活动任务发生这些变化时，发送带原绑定的停止结果，标记 ABORTED，清除段基线，使地图位置/朝向上下文失效。
- 空闲或已完成时发生坐标重置，也使原地图绑定失效，不能继续声称仍位于旧节点。
- 新会话的有效里程只代表新的局部坐标已建立，不代表地图位置已确认。
- 在人工确认新地图起点、朝向并完成执行上下文初始化之前，禁止从旧 `current_node` 自动开始下一段。
- 第一次启动已配置的起点可按现有独立启动方式建立初始绑定；之后的坐标变化不能静默重新套用旧初始位置。

### 7.2 mission

- 继续独占正式比赛的最终速度输出；不让通信节点与 mission 竞争发布 `/C/controll`。
- 校验并原样转发自动指令的坐标会话/许可代次，清除过期缓存。
- 增加真实 C 板状态与里程会话监视；比赛活动期间异常立即停止底盘转发，阻止派发后续路线，进入现有故障/停止处理流程。
- 即使异常发生在区域等待或非导航阶段，也不能沿用旧地图绑定继续派发下一条路线。
- 保留 MOCK 与 REAL 的现有隔离；模拟运行不得因为新增真实 C 板依赖而无法启动，也不能把 MOCK 指令转发到真实车。
- 正常比赛流程：起点摆车 → 切 PC 建原点 → mission 初始化地图上下文 → 开始比赛。异常自动恢复仅恢复通信，不自动恢复比赛阶段或机械臂动作。

## 8. 调试工具迁移

### 8.1 中止与重新开始

1. 记录当前坐标会话及运动许可代次，贯穿初始化、导航、区域等待、READY 和完成后的地图显示。
2. 运行中切 RC、重连、重启或会话/许可变化：立即清除速度转发和等待倒计时，终止本轮任务，撤销地图锚定。
3. 显示“坐标/控制状态已变化，请重新选择当前位置和朝向后开始”。停止确认后开放设置。
4. 用户重新选择当前位置和朝向，再点击“开始”；工具执行新的上下文初始化后派发新任务，不强制用户先在终端清锁，也不增加一次必须先点“复位”的隐藏步骤。
5. 启动、停止、RPC 结果未知等处理中继续保持现有去重和结果确认规则；不能以自动恢复为由重复提交尚未明确是否执行的运动请求。
6. “复位”按钮继续允许显式准备上下文，但不再清通信锁，也不会额外归零里程或驱动车辆回起点。

### 8.2 从实测 x/y 建立地图锚定

点击开始、人工确认节点和朝向后，记录本轮新鲜反馈 `(xa,ya,yawa)` 以及所选节点、朝向，作为地图锚定。它允许在同一 PC 会话内从非零里程位置开始另一轮任务，无需强制再拨一次遥控。

当前反馈相对锚定姿态的位移：

```text
d_local = (x_now-xa, y_now-ya)
d_body_at_anchor = M(-yawa) * d_local
```

令所选地图朝向对应的顺时针屏幕角为 `h`，在“地图右/下”的平面中：

```text
forward = (sin(h), -cos(h))
left = (-cos(h), -sin(h))

d_map = forward * d_body_at_anchor.x + left * d_body_at_anchor.y
display_angle_deg = heading_angle_deg - degrees(yaw_now-yawa)
```

先在米制地图平面转换，再按地图标定映射到截图像素；不要把米与像素直接相加。

截图有非均匀像素锚点，逐边配置长度也可能不相等。显示映射应使用独立的米制地图节点和像素标定：默认依据现有网格及加载边长建立近似标定，必要时允许在调试配置中给出实测地图节点坐标。若边长不能组成一致网格，给出标定不一致说明，保留米制实测 x/y，不把各条边单独缩放成“看起来总能准确到节点”。像素映射只用于显示，不反馈到运动控制。

### 8.3 界面

- 规划路线继续按节点绘制；实测轨迹按反馈 x/y 连续映射，不按段进度贴在道路中心，不在 COMPLETED 时强行吸附到终点。
- 显示会话位置 x/y、连续航向、车体系实际 vx/vy/wz；输入指令另列，标签统一为“前 / 左 / 转”。
- 显示当前段目标、纵向投影进度、横向偏差、坐标状态和运动许可。
- 删除旧“累计里程”数值及 JSON 字段依赖；可显示当前段投影距离，名称不能仍叫累计里程。
- 保留原图、九节点编号、两种模式、固定工作朝向及模拟比赛 8 条路线/7 次等待，不扩大本次业务范围。
- 原点改变时断开旧轨迹，不能画出连接两个不同坐标会话的假直线；保留失效提示和事件日志。
- 标注“实测里程轨迹”：仍受轮式里程与 IMU 漂移影响，不将其称为绝对定位。

## 9. yaw 漂移与三秒运动的诊断计划

### 9.1 静止航向采样

新增只读采样工具或等效可复现脚本，同时记录原始 yaw、会话 yaw、原始 wz、速度、x/y、板端时间、状态位、控制权、坐标会话及许可代次。

- 用户确认车辆静止后，分别采集启动早期和稳定运行后的 60 秒数据；不由工具下发运动。
- 计算原始 yaw 随时间斜率、角速度平均值及其积分，与会话航向差值比较。
- 同一会话内，局部 yaw 只是原始 yaw 减固定零点，漂移趋势应一致；每次重置只改变零点，不能消除漂移。
- 若原始 yaw 在物理静止时持续变化，向电控提供时间段、漂移率、wz 和状态，建议检查静止零偏、陀螺单位、积分 dt、标定时机及融合处理。
- 若原始反馈正常、局部值异常，再检查上位机坐标变换、会话切换和单位换算。

### 9.2 三秒低速运动验证

新增专用低速定时发布测试入口：

1. 等待最终速度话题的订阅匹配和 C 板就绪，确认没有其他速度发布者。
2. 从第一条实际非零发布开始以单调时钟计时，50 Hz 发布整三秒，而不是对 ROS CLI 启动进程的总时长计时。
3. 前进使用 `vx=0.05, vy=0, omega=0`；三秒到达后主动发送零速并停止非零发布。
4. 记录实际发布起止、通信输入有效性、串口实际 mode/速度、状态变化、下位机实际速度和位置差。
5. 若提前停止，区分输入间断、时间戳拒绝、非 PC、反馈超时、健康异常、串口问题或板端未执行；保留首次原因与持续时间。

可在原有串口线程记录轻量诊断并由 ROS 侧周期汇总，不在 50 Hz 热路径逐帧刷屏。无需为诊断让通信节点发布到自己的输入话题。

名义 0.05 m/s × 3 s 为 0.15 m，只作为理想参考；物理位移还受板端加减速、低速响应和地面条件影响。不能把未达到 150 mm 直接判为通信故障。

## 12. 验证与验收矩阵

### 12.1 不连接硬件的核心验证

| 用例 | 必须满足 |
| --- | --- |
| vx 单独为正 | 编码为板端前向速度，不交换轴 |
| vy 单独为正 | 编码为板端左向速度 |
| 角速度输入 90 deg/s | 编码为 pi/2 rad/s，符号不变 |
| 无输入或输入年龄超过 0.05 s | 周期零速，旧命令不续命 |
| 非零原点、yaw0=90° 后沿原点车头前进 | 新 x 增加，新 y 约为零，局部 yaw 约为零 |
| 局部 yaw=90° 时沿当前车头前进 | 固定 y 增加，固定 x 约不变 |
| yaw 连续跨 360° | 不回绕，不误判倒转 |
| source 连续多帧等于 2 | 只初始化一次，不每帧归零 |
| RC→PC、重连、节点重启、板端重启 | 新会话，第一条有效坐标归零，旧绑定失效 |
| 健康异常恢复 | 无人工清锁，原点连续时保留坐标，旧许可代次不能执行 |
| uint32 板端时钟自然回绕 | 不当成重启，不重复初始化 |
| STATUS/ODOM 交错或重复帧 | 不引起双重重置或伪造新鲜度 |
| 正方向、反方向、纯横向、原地转动 | 仅目标方向投影推进当前平移段 |
| 往复抖动 | 不靠总路程累计或反复刷新“进展”无限维持任务 |

### 12.2 ROS2 与伪串口集成

- 验证 50 Hz 下发节奏、空闲零速、输入消失后归零的实际延迟与时间戳拒绝原因。
- RC 与 PC 下新里程均发布；切回 PC 状态原因自动更新，坐标只重建一次。
- 模拟轮离线、IMU/打滑异常、反馈超时、串口重连和板端时间重启；恢复可执行新任务，旧自动指令被绑定检查拒绝。
- 更新假板模型：正确积分前/左车体系到固定位置，并上报对应的实际速度，不能始终用零速度占位。
- 模拟规划器、mission、浏览器完整链路，涵盖前后左右、转向、合并动作和到点停车。
- 无真实 C 板时运行 MOCK 仍然可用，且不会发布真实底盘非零命令。

### 12.3 浏览器与任务流程

- 手动给假反馈增加横向位移，图标和轨迹必须显示偏离道路，不能吸附回规划线。
- 正常完成时保留实际终点偏差；状态显示成功不篡改位置。
- 导航、工作等待和 READY 状态下切 PC 重置均撤销旧地图锚定。
- 停止确认后重新选择位置与朝向，直接点“开始”能初始化新任务；不要求手动调用服务清锁。
- 旧会话延迟反馈和旧异步 RPC 返回不能重新激活旧任务。
- 保留模拟比赛 8 段路线、7 次真实 3 秒等待及当前工作朝向。
- 保留单一最终速度发布者、浏览器失联停车、重复操作去重及停止结果确认。

### 12.4 实车验收

1. 无运动输入：确认串口持续零速，`/C/status` 更新，原始与会话里程只随新采样更新。
2. 低速左移、前进、逆时针逐项确认控制轴和实测反馈轴。
3. 在不同位置、不同朝向切回 PC，确认本次原点为零、坐标轴跟随重置时朝向固定建立。
4. 绕车身转向后前进，核对固定坐标变化与车体系速度的区别。
5. 调试导航中切 RC 再切 PC，确认旧任务终止、状态自动恢复、需重新选择位置后开始。
6. 测试节点重启、串口重连和 C 板重启；每次均重建坐标，不自动续跑。
7. 连接完成后实际发布三秒低速，核对指令持续时间、实际速度、位置和停止原因。
8. 静止采样确认 yaw 漂移量及其板端来源，保存给电控的记录。
9. 地面短段及转向测试后记录纵向终点误差、横向偏差和停车惯性，不用 A 方案宣称已具备二维闭环精度。

实车控制不在本次计划书编写阶段执行；实施完成后，自动化通过与实车验收结果分别记录。
