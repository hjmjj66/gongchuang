# C 板速度下发核对记录

日期：2026-10-26。范围：仓库内协议、ROS 最终指令到串口的路径、诊断入口及伪串口验证。未连接实车；仓库没有 C 板固件源码，无法验证板端实际执行分支。

## 结论

通信桥接实现与当前《上位机通信协议(4).md》的速度载荷一致，未发现桥接把单轴速度混为双轴、交换字段、重复旋转或角速度单位换算错误。

发现并修复了诊断 CLI 的隐含前进速度：旧版 `cboard_diagnostics pulse` 的 `--vy` 默认 `0.05`，只指定 `--vx` 或 `--omega` 会同时下发前进速度。如果现场使用的是该入口且未显式设置 `--vy 0`，就能直接解释斜走或边走边转。尚未取得现场完整命令，不能认定它就是本次实车现象的根因。

## 协议与实现逐项核对

| 项目 | 协议与实际代码 |
| --- | --- |
| ROS 速度语义 | `ControlCommand.vx_mps` 当前车身左向，`vy_mps` 当前车头前向，单位 m/s |
| 线速度映射 | `_on_command` 原样取两个字段，`ChassisAdapter.on_command` 原顺序传给编码器，无交换或取反 |
| 角速度 | ROS `omega_deg_s` 单位 °/s；`math.radians` 转一次后以 rad/s 写入 `wz`，符号不变 |
| 载荷布局 | `<fffB3x`，16 B；偏移 0/4/8 为 vx/vy/wz，12 为 mode，13–15 为零 |
| 完整帧 | `AA 55 01 10` + 16 B 载荷 + 小端 CRC16，共 22 B |
| CRC | 对 MSG_ID、LEN、PAYLOAD 计算，初值 FFFF、多项式 A001、无末异或；协议示例帧全部匹配 |
| 速度坐标变换 | 发送路径无 yaw 旋转；`local_odom` 的旋转只处理反馈位置和原点，不修改待发速度 |
| C 板内部坐标 | 协议规定板端执行 `vx_int=-vx_proto, vy_int=vy_proto`；上位机不重复执行该转换，固件是否落实需电控确认 |
| 周期与超时 | YAML 50 Hz；锁存最新完整指令重发，输入源时间超过 50 ms 后下一发送周期发零；非许可状态发零 |
| mode | 有效非零速度为 1；全零、无输入、超时或无许可为 0，不为 mode=1 的主动零速控制 |
| 串口写入 | 原帧写出，不重排载荷；短写按断连处理；`sent_*` 从成功写入的帧反解 |

协议把 CRC 称为 ARC，但所列参数和校验值实际对应通常命名的 CRC-16/MODBUS；实现采用文档明确的参数，两端核对时应以参数和示例字节为准。这个名称问题不会自行引入双轴速度。

规划器平移命令也是单轴：前后只用 vy，左右只用 vx，角速度为零；mission 原样转发已校验的完整指令。当前方案没有平移航向保持或横向纠偏。`wz=0` 表示目标角速度零，不包含“锁定平移开始时航向”的上位机闭环。

旧《C板底盘通信节点实施计划》的正文保留了迁移前“ROS 前 vx / 左 vy，并在桥接交换轴”的历史说明，文件顶部已声明失效。当前消息、协议、源码、README 和操作指南统一为“左 vx / 前 vy”，不能照旧表额外交换。

## 已修复与验证

`diagnostics.py` 的 `--vy` 默认值由 `0.05` 改为 `0`。未指定的三个速度轴现在均为零，前进必须显式指定 `--vy`。同步更新节点 README 与实车测试指南。

新增核心验证：多个原点航向、运动中航向变化下，分别给正负 vx、vy、omega，直接按协议偏移反解输出帧，确认无附加速度、角速度转换正确、mode/保留字节正确。

扩充已安装 CLI 的 ROS/PTY 集成验证：`--vx 0.05` 只横移、`--omega 10` 只旋转、不填速度只发零，同时保留显式 vy 的三秒周期测试和停止检查。

- 20 项协议/核心测试通过。
- `agv_cboard` 重新构建成功。
- 3 项 ROS/PTY 集成测试通过，仅使用软件创建的伪串口。

## 待现场与电控确认

1. 现场完整命令及实际入口；是否显式把非目标速度轴置零？斜移时车头是否也旋转？
2. PC 分支是否严格按小端 float32 的偏移 0/4/8/12 解析 vx/vy/wz/mode？请提供接收后的原始三个目标值，尤其是单轴指令时另两轴是否精确为零。
3. 固件是否把 PC 的 vx/vy 视为当前车体系左/前，并且仅做一次协议到内部的符号转换？是否存在额外场地系转换、yaw 旋转或进入 PC 时的参考角偏置？
4. PC 和摇杆是否共用同一麦轮解算及四轮编号/符号？相同速度下，滤波、死区、最小输出、斜坡和航向保持是否一致？需要比较进入轮速解算前的 vx/vy/wz 及四轮目标转速，而不只比较最终车轮反馈。
5. PC 分支如何处理 mode=0 与 mode=1 的全零指令？是否在模式变化时重置 PID、滤波或航向参考？这用于确认 50 ms 输入超时导致的间歇归零是否与板端控制状态有关。

## 现场定位依据

同一次单轴试验同时看 `/C/controll`、`/C/status` 的 `sent_vx_mps/sent_vy_mps/sent_wz_rad_s/sent_mode`，并对比电控收到的原始目标值。`sent_*` 证明上位机成功写出的帧内容，不证明板端已接收或执行；20 Hz 状态只展示最近一帧，不能替代完整瞬态抓包。

- 输入或 `sent_*` 已有两个非零轴：先查命令入口与发布者；直接 `ros2 topic pub` 时桥接没有独占发布者拦截，多个发布者会覆盖最新完整命令，桥接不会将两者做向量相加。
- 上位机发出的另两轴均为零、板端接收却不是零：查固件帧解析、结构体对齐和内存覆盖。
- 板端接收正确、进入轮速解算前出现另一速度轴：查 PC 分支坐标旋转、混控与状态保留。
- 进入解算前仍是纯单轴：比较 PC/摇杆的四轮目标，再检查轮控与底盘响应。

肉眼可见的实际斜走不能仅用里程显示旋转解释；但遥控能直走只说明该路径正常，尚不能单凭这一点排除 PC 分支的轮控参数或低速响应差异。
